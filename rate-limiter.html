1. Start with requirements

Functional

Allow or reject a request based on a limit. Key the policy by API key, user, IP, tenant, endpoint, or a hierarchy of keys.

Non-functional

Very low decision latency, high availability, predictable memory/CPU, horizontal scalability, and safe behavior during datastore failures.

Policy examples

100 req/min/user, 1,000 req/s/tenant, burst capacity of 2,000, separate read/write limits.

Questions to clarify

Hard vs soft limit? Burst allowed? Exact vs approximate counting? Per-region or global? What should happen when the limiter store is unavailable?

Interview framing: first define the limit, window, identity key, burst semantics, and consistency requirement. The algorithm follows from those choices.

2. Reference architecture

Client
→
API Gateway / Service
→
Rate Limiter
→
Protected API

Local fast path

Each application instance keeps counters/tokens in memory. Lowest latency; no network hop. Accuracy is approximate when many instances share a quota.

Shared state

Redis is a common choice for a shared limiter. Use atomic operations or a Lua script so read/decide/update is one atomic decision.

Hybrid

Use local checks for coarse protection and Redis for tenant/global quotas. This limits blast radius while preserving accurate shared limits where required.

Request path

1. Extract identity: tenantId / userId / IP
2. Load policy: rate + burst + algorithm
3. Atomically evaluate limiter
4. If denied: HTTP 429 + Retry-After
5. If allowed: forward request
6. Emit metrics: allowed, rejected, remaining, decision latency

3. Algorithms at a glance

AlgorithmIdeaBurst behaviorMemoryTypical use
Fixed WindowCount requests inside fixed time buckets.Can burst at a boundary.O(keys)Simple API quotas.
Sliding Window LogStore timestamps of recent requests.Precise; no boundary artifact.O(requests in window)Smaller traffic / strict precision.
Sliding Window CounterCombine current and previous window counts using a weighted estimate.Smoother than fixed window.O(keys)Large scale, approximate limits.
Token BucketTokens refill continuously; requests consume tokens.Explicit burst capacity.O(keys)APIs and traffic shaping.
Leaky BucketRequests enter a bounded queue drained at a steady rate.Buffers burst; queue can fill.O(queue)Smoothing work into a downstream system.
Key distinction: token bucket controls how many requests may pass immediately; leaky bucket controls the output rate and commonly introduces a queue.

4. Simple Java implementations

These examples are intentionally small and in-memory. They show the core algorithm, not production concerns such as distributed atomicity, eviction, persistence, or configuration management.

4.1 Fixed Window Counter

import java.time.Duration;
import java.util.concurrent.ConcurrentHashMap;

public final class FixedWindowRateLimiter {
    private final long limit;
    private final long windowMillis;
    private final ConcurrentHashMap<String, Counter> counters = new ConcurrentHashMap<>();

    public FixedWindowRateLimiter(long limit, Duration window) {
        this.limit = limit;
        this.windowMillis = window.toMillis();
    }

    public boolean allow(String key) {
        long now = System.currentTimeMillis();
        long window = now / windowMillis;

        Counter c = counters.compute(key, (k, old) -> {
            if (old == null || old.window != window) {
                return new Counter(window, 1);
            }
            return new Counter(old.window, old.count + 1);
        });

        return c.count <= limit;
    }

    private record Counter(long window, long count) {}
}
Boundary issue: a client can make limit requests at the end of one window and another limit immediately after the boundary.

4.2 Sliding Window Log

import java.time.Duration;
import java.util.ArrayDeque;
import java.util.Deque;
import java.util.concurrent.ConcurrentHashMap;

public final class SlidingWindowLogRateLimiter {
    private final int limit;
    private final long windowMillis;
    private final ConcurrentHashMap<String, Deque<Long>> logs = new ConcurrentHashMap<>();

    public SlidingWindowLogRateLimiter(int limit, Duration window) {
        this.limit = limit;
        this.windowMillis = window.toMillis();
    }

    public boolean allow(String key) {
        long now = System.currentTimeMillis();

        Deque<Long> q = logs.computeIfAbsent(key, k -> new ArrayDeque<>());
        synchronized (q) {
            long cutoff = now - windowMillis;
            while (!q.isEmpty() && q.peekFirst() <= cutoff) {
                q.removeFirst();
            }
            if (q.size() >= limit) {
                return false;
            }
            q.addLast(now);
            return true;
        }
    }
}

Exact within the chosen clock/window, but memory grows with request volume.

4.3 Sliding Window Counter

public final class SlidingWindowCounterRateLimiter {
    private final long limit;
    private final long windowMillis;

    private long currentWindow = -1;
    private long currentCount = 0;
    private long previousCount = 0;

    public SlidingWindowCounterRateLimiter(long limit, long windowMillis) {
        this.limit = limit;
        this.windowMillis = windowMillis;
    }

    public synchronized boolean allow() {
        long nowWindow = System.currentTimeMillis() / windowMillis;

        if (currentWindow == -1) {
            currentWindow = nowWindow;
        } else if (nowWindow != currentWindow) {
            previousCount = currentCount;
            currentCount = 0;
            currentWindow = nowWindow;
        }

        double elapsedFraction =
                (System.currentTimeMillis() % windowMillis) / (double) windowMillis;

        double estimated = previousCount * (1.0 - elapsedFraction) + currentCount;

        if (estimated >= limit) {
            return false;
        }

        currentCount++;
        return true;
    }
}

In a real service, keep two counters per key and use an atomic datastore operation. This algorithm is an estimate, not an exact timestamp log.

4.4 Token Bucket

public final class TokenBucketRateLimiter {
    private final double capacity;
    private final double refillPerSecond;

    private double tokens;
    private long lastRefillNanos;

    public TokenBucketRateLimiter(double capacity, double refillPerSecond) {
        this.capacity = capacity;
        this.refillPerSecond = refillPerSecond;
        this.tokens = capacity;
        this.lastRefillNanos = System.nanoTime();
    }

    public synchronized boolean allow() {
        refill();

        if (tokens < 1.0) {
            return false;
        }

        tokens -= 1.0;
        return true;
    }

    private void refill() {
        long now = System.nanoTime();
        double elapsedSeconds = (now - lastRefillNanos) / 1_000_000_000.0;

        tokens = Math.min(capacity, tokens + elapsedSeconds * refillPerSecond);
        lastRefillNanos = now;
    }
}
Example: capacity = 100 and refill = 10 tokens/sec means up to 100 immediate requests after a full idle period, then roughly 10 requests/sec sustained.

4.5 Leaky Bucket

import java.time.Duration;
import java.util.ArrayDeque;
import java.util.Queue;

public final class LeakyBucketRateLimiter {
    private final int queueCapacity;
    private final long intervalMillis;
    private final Queue<Long> queue = new ArrayDeque<>();
    private long nextLeakAt = 0;

    public LeakyBucketRateLimiter(int queueCapacity, Duration outputInterval) {
        this.queueCapacity = queueCapacity;
        this.intervalMillis = outputInterval.toMillis();
    }

    public synchronized boolean submit(long requestId) {
        drain(System.currentTimeMillis());

        if (queue.size() >= queueCapacity) {
            return false; // shed load when the buffer is full
        }

        queue.add(requestId);
        return true;
    }

    public synchronized Long pollReady() {
        drain(System.currentTimeMillis());
        return queue.poll();
    }

    private void drain(long now) {
        if (queue.isEmpty()) {
            nextLeakAt = now;
            return;
        }
        if (now >= nextLeakAt) {
            nextLeakAt = now + intervalMillis;
        }
    }
}
Production note: a real leaky bucket is normally implemented with a worker/scheduler that drains the queue at a controlled rate. The example focuses on the queue + overflow semantics rather than thread scheduling.

Which implementation should I code in an interview?

Token bucket is usually the cleanest choice when the interviewer asks for configurable rate + burst behavior. For a strict "N requests per minute" requirement, start with fixed window and then explain why you would move to sliding window or token bucket if boundary bursts matter.

5. Distributed / multi-instance design

Suppose there are 100 application pods. A local limiter with a limit of 100 requests/sec per pod does not enforce a global 100 requests/sec tenant quota. Shared state is required when the quota is global.

Why atomicity matters

Bad:
GET count
if count < limit
  INCR count

Two servers can both read the same old count and both allow.

Better:
One atomic Redis operation / Lua script:
  1. read state
  2. expire old state
  3. calculate allowance
  4. update state
  5. return allowed + remaining + retryAfter

Useful Redis response contract

  "allowed": true,
  "remaining": 42,
  "retryAfterMs": 0,
  "limit": 100,
  "resetAtMs": 1750000000000
}

NeedGood fitWhy
Very simple per-minute quotaFixed windowSmall state and easy implementation.
Precise recent-request countSliding logTracks timestamps directly.

Staff-level discussion: do not stop at the algorithm. Explain identity cardinality, shared-vs-local state, atomicity, multi-region behavior, fallback mode, observability, and cost.

Questions interviewers commonly ask

How do you make it accurate across 50 pods?

Use shared atomic state, or explicitly choose approximate local accounting. State why the consistency requirement justifies the network hop.

How do you support 10M tenants?

Prefer compact per-key state, TTL inactive keys, avoid timestamp logs at huge cardinality, and control policy/cache memory separately from request state.

How do you handle global multi-region quotas?

Choose between a globally coordinated limiter, regional quota allocation, or an intentionally approximate model. The right answer depends on whether hard global enforcement is mandatory.

What metrics matter?

Allowed/rejected rate, decision latency p50/p95/p99, Redis errors/timeouts, hot keys, remaining quota distribution, local fallback usage, and false-rejection indicators.

A strong closing answer

"For an API with bursty traffic, I would start with token bucket because it expresses
both a sustained rate and burst capacity. In a multi-pod deployment, I would keep the
authoritative bucket in Redis and evaluate/update it atomically. I'd add local
protection as a fallback, define fail-open vs fail-closed by endpoint criticality,
return Retry-After on 429s, and monitor decision latency plus rejection/error rates.
If global multi-region enforcement is required, I'd revisit the state model because
cross-region coordination becomes the dominant trade-off."
